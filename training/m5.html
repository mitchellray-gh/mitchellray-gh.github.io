5.2Matching slots to fields: bipartite matching

The setup

Build a bipartite graph:

  • Left nodes: the template slots, written S = {s1, …, sm}
  • Right nodes: the candidate fields, written F = {f1, …, fn}
  • Edge weights: w(s, f) = how well field f represents slot s

Weights come from the Module 2 signals: embedding similarity between names and descriptions, the lexicon, type compatibility (a measure needs a numeric field, a time slot needs a date field) and curated metadata.

“Bipartite” just means two groups: the things we are looking for (slots) on one side and the things we could use (columns) on the other. Lines connect them, and each line has a score for “how good a fit is this?”.

The objective

Choose a matching M: a set of slot–field pairs in which no slot and no field is used twice.

M* = argmax_M Σ_{(s,f) ∈ M} w(s, f)

choose the one-to-one pairing whose scores add up to the biggest total.

If each weight is a log probability, w(s, f) = log P(f represents s), then maximizing the sum is the same as maximizing the joint probability that all the matches are right. This is the same trick used for join paths in Module 3.

Why greedy fails

Greedy matching takes the single best pair first, then the best remaining pair, and so on. Here is a small case where that goes wrong:

amountsales_total
Revenue0.900.80
Refund0.850.10

amount is a generic name, so it fits both concepts. sales_total only fits Revenue.

Greedy: Revenue → amount (0.90), then Refund → sales_total (0.10) total = 1.00 Optimal: Revenue → sales_total (0.80), Refund → amount (0.85) total = 1.65

Greedy grabbed the most attractive pair and left Refund with a nonsense match. The optimal solution gives up a little on Revenue to gain a lot on Refund.

Seating guests at a wedding: if you give the loudest guest their first-choice seat without looking at anyone else, you can end up putting the person who only gets along with that seat’s neighbour at the far end of the room. A good planner looks at the whole table.

The Hungarian algorithm (intuition)

The Hungarian algorithm finds the optimal matching in O(n³) time. The idea:

  1. Turn it into a cost-minimization problem (cost = max weight − weight).
  2. Subtract each row’s minimum, then each column’s minimum, so that zeros mark “best available” choices.
  3. Look for a full set of zeros in which no two share a row or column. If none exists, adjust the costs and repeat.

The result is the globally best assignment, never a locally greedy one.

Walk-through on the Revenue / Refund table (added illustration)

Cost = 0.90 − weight: amount sales_total Revenue 0.00 0.10 Refund 0.05 0.80 Subtract row minima (0, 0.05): Revenue 0.00 0.10 | Refund 0.00 0.75 Subtract column minima (0, 0.10): Revenue 0.00 0.00 | Refund 0.00 0.65 Zeros: (Revenue, amount), (Revenue, sales_total), (Refund, amount) Full set with no shared row or column: Revenue → sales_total, Refund → amount ✓

Practical variations

VariationWhen it applies
Unmatched slotNo field has w ≥ τ, so leave the slot empty and fill it with a prior, or ask (Module 3, section 3.9)

Because the “one field serving two slots” case breaks the one-to-one rule, the matching is allowed to reuse a column across a dimension slot and a filter slot. In the calculator above you can mimic a hard type constraint by typing a very negative weight such as −9.

5.3Validating values against the data

A literal value in the question (“EMEA”, “California”, “Gold”) must actually exist in the matched field. Otherwise the query returns nothing, or the wrong rows.

Three levels of lookup

LevelRuleExample
Exactv ∈ V(f)“EMEA” = “EMEA”
Normalizednorm(v) ∈ norm(V(f)), ignoring case, spaces and punctuation“emea ” → “EMEA”
Fuzzymax_{u ∈ V(f)} sim(v, u) ≥ τ_v“Calfornia” → “California”

Fuzzy example: “Calfornia” vs. “California” is one insertion apart, and the longer word has 10 letters.

sim = 1 − 1/10 = 0.90 ≥ τ_v = 0.85 ⇒ accept, and mention the correction

Try the exact spelling first, then ignore capital letters and stray spaces, and only then allow “close enough” typos. The more forgiving the lookup, the more clearly the system should tell you what it assumed.

The similarity used here is edit distance based: sim = 1 − (number of single-letter edits) / (length of the longer word). The widget below computes it for you with the Levenshtein distance.

Which column holds the value?

Sometimes the value is known but the field isn’t. “Revenue from Gold customers”: where does “Gold” live? Treat it as Bayesian inference over the candidate fields:

P(f | v) ∝ P(v | f) · P(f | slot)
  • P(v | f) is how common v is in field f.
  • P(f | slot) is how well the field’s type fits the slot. The template expects a customer attribute.
FieldRows with “Gold”P(v | f)P(f | customer slot)Product
customer_tier1,200 of 10,0000.120.80.096

The ratio is 0.096 / 0.00006 = 1,600 : 1 in favour of customer_tier.

You hear the word “Gold” in a crowded room. Is someone talking about a customer tier or a paint colour? Two clues decide it: how often is that word used in each topic, and which topic fits the sentence you are in. Multiply both clues together.

The empty-result check

A query that returns zero rows is strong evidence that a value or filter is wrong, rather than evidence that the true answer is zero:

if |result| = 0: re-check each filter value → relax filters one at a time → find which one empties the result

5.4Combining confidence across stages

Every stage so far produced a probability. If the stages are roughly independent, the probability that everything is right is their product:

Conf = Πᵢ pᵢ log Conf = Σᵢ log pᵢ

the chance that every step is right is each step’s chance multiplied together, so it can only get smaller.

A relay race of five runners who each have a 75–90% chance of a clean baton pass. Every handover seems safe, but the chance that all five are clean is well under half. One dropped baton ruins the race.

Which stage should we clarify?

Asking the user to settle a stage raises that stage’s pi to 1. The new overall confidence becomes Conf / pi, so the lowest pi gives the largest gain.

Ask about the weakest link. One well-chosen clarifying question beats several vague ones.

When stages are not independent

If two stages depend on each other (for example, the entity choice makes a particular source more likely), the simple product under-counts confidence. The general form is the chain rule:

P(all correct) = P(s₁) · P(s₂ | s₁) · P(s₃ | s₁, s₂) · …

5.5Sanity checks: does the answer look plausible?

Even a well-built plan can produce an implausible number, often because of a join trap (Module 3, section 3.7) or a wrong filter. Sanity checks compare the answer with what we’d expect.

It is the “does that smell right?” check an accountant does before sending a report: is it close to last time’s figure, is it wildly out of the usual range, and do the parts add up?

Check 1: Consistency with a reference value

If an independent reference Aref exists (a curated report, a different source), measure agreement:

Consistency(A) = exp( −η · |A − A_ref| / |A_ref| )

Example: A = $1.05M, Aref = $1.00M and η = 2. The relative gap is 5%.

Consistency = exp(−2 × 0.05) = e^(−0.1) ≈ 0.905

A 50% gap gives e−1 ≈ 0.37: a strong signal that something differs, such as the definition, the filters or the time window.

Check 2: Robust outlier score

Compare the result with the history of the same metric. Plain z-scores are distorted by past outliers, so use the median and the median absolute deviation (MAD):

modified z = 0.6745 · (x − median) / MAD flag if |modified z| > 3.5

Example: monthly revenue has a historical median of $1.00M and a MAD of $0.08M. The new result is $3.10M.

modified z = 0.6745 × (3.10 − 1.00) / 0.08 = 0.6745 × 26.25 ≈ 17.7 ⇒ flag

A value of about 3× normal is the classic signature of a fan-out join (Module 3).

“MAD” is the typical wiggle of the metric month to month. The modified z-score counts how many typical wiggles away the new number is. Beyond about 3.5 wiggles, something is probably wrong with the query, not the business.

Check 3: Structural invariants

These are rules that must always hold:

InvariantViolation suggests
COUNT(DISTINCT customers) ≤ total customersDuplicated rows
Shares of a whole sum to ≈ 100%Overlapping categories, or missing ones
Non-negative measures stay ≥ 0Sign errors, refunds mixed in
Sub-totals add up to the totalInconsistent filters across parts
A rate stays between 0 and 1Numerator and denominator at different grains

Updating confidence after a red flag

A failed check is evidence. Use Bayes’ rule to update the prior confidence:

P(correct | flag) = P(flag | correct) · P(correct) / P(flag)

Example: prior P(correct) = 0.8. Correct answers rarely trigger the flag, so P(flag | correct) = 0.02. Wrong answers often do, so P(flag | wrong) = 0.5.

P(flag) = 0.02 × 0.8 + 0.5 × 0.2 = 0.016 + 0.100 = 0.116 P(correct | flag) = 0.016 / 0.116 ≈ 0.14

Confidence drops from 80% to 14%. The right response is to re-examine the plan, not to report the number.

A smoke alarm that almost never goes off in a tidy kitchen (2%) but usually goes off when something is burning (50%). When it rings, you stop trusting “everything is fine” and go look, even if you were 80% sure dinner was fine.

5.6Ranking and retrieval: two stages

There may be thousands of candidate sources or plans. Scoring each one in depth is too slow, so rankers work in two stages:

Stage 1 (recall): cheap score over everything → keep the top K (e.g. K = 50) Stage 2 (precision): rich score over those K only → final order

Hiring: a quick CV screen over 1,000 applicants picks 50 to interview (Stage 1, cheap and broad). The long interviews only happen with those 50 (Stage 2, rich and slow). If the CV screen drops the best person, no interview can bring them back.

Stage 1: retrieve broadly

  • Embedding nearest-neighbour search with cos(φ(Q), φ(d)) (Module 1), plus a keyword score.
  • Approximate nearest-neighbour methods trade a little accuracy for very large speed-ups.
  • The goal is not to miss anything relevant. It’s measured by recall at K:
Recall@K = | relevant items in top K | / | all relevant items |

If Stage 1 misses a relevant item, Stage 2 can never recover it. Stage 1 errors are permanent.

Stage 2: re-rank precisely

Score each of the K survivors with a richer function of many features:

r(Q, d) = f_θ( cos, BM25, concept coverage, prior P(d), field-match quality, value-validation pass, sanity score, … )

The simplest form is linear, r = Σⱼ θⱼ · xⱼ. More expressive forms (trees, neural networks) capture interactions between features.

The trade-off

KEffect
SmallFast, but Recall@K falls and good candidates are lost
LargeSlow, but Stage 2 sees more good candidates

Choose K as the smallest value at which Recall@K reaches a target, such as 95%.

5.7Learning to rank

How do we choose the weights θ? We learn them from examples of good and bad rankings. There are three families of objectives.

Show the system many examples where humans said “this one is better than that one”, and nudge the weights until its scores agree. The three families differ in what they ask the system to get right: each score, each pair, or the whole list.

Pointwise: predict each item’s relevance

ℒ = Σ_d ( r(Q, d) − label(d) )² or cross-entropy for yes/no labels

This is simple, but it optimizes absolute scores, while ranking only cares about order.

Pairwise: get pairs in the right order

For each pair (d⁺ more relevant than d⁻), penalize the ranker when d⁻ scores close to or above d⁺:

ℒ_pair = log( 1 + exp( −( r(d⁺) − r(d⁻) ) ) )
ScoresGap r(d⁺) − r(d⁻)Loss
r(d⁺) = 2, r(d⁻) = 1 (correct order)+1ln(1 + e−1) ≈ 0.313
r(d⁺) = 1, r(d⁻) = 1 (tied)0ln 2 ≈ 0.693
r(d⁺) = 1, r(d⁻) = 2 (wrong order)−1ln(1 + e1) ≈ 1.313

The loss shrinks smoothly as the correct item pulls ahead, and grows as the order flips.

Listwise: optimize the whole list

Treat the scores as a probability distribution over which item belongs at the top, and match it to the ideal distribution:

P_θ(d at top) = softmax_d( r(Q, d) ) ℒ_list = −Σ_d P_ideal(d) · log P_θ(d at top)

Listwise methods most directly target metrics like nDCG (section 5.9), because they weight mistakes near the top more heavily.

FamilyOptimizesStrengthWeakness
PointwiseEach scoreSimpleIgnores order
PairwisePair orderRobust and intuitiveTreats all pairs equally
ListwiseWhole listMatches ranking metricsMore complex

5.8Diversity: maximal marginal relevance (MMR)

A ranking full of near-duplicates wastes the top positions. Three copies of the same table rank highly, but tell the user nothing new.

The MMR rule

  • λ = 1: pure relevance (no diversity)
  • λ = 0: pure novelty (ignores relevance)

Build the list one item at a time. Each pick balances relevance against similarity to what has already been chosen:

next = argmax_{d ∉ S} [ λ · r(Q, d) − (1 − λ) · max_{s ∈ S} sim(d, s) ]

pick the item that is relevant but not a copy of something already on the list.

Choosing a playlist for a road trip: you want the best songs, but not the same song three times in a row. Each new pick must be good and different from what is already queued.

Worked example (λ = 0.7)

Candidater(Q, d)sim to d1
d1 certified summary table0.90—
d2 copy of d1 in another workspace0.880.95
d3 detailed transaction table0.700.20

Pick 1: nothing is selected yet, so choose the most relevant: d1.

Pick 2:

MMR(d₂) = 0.7 × 0.88 − 0.3 × 0.95 = 0.616 − 0.285 = 0.331 MMR(d₃) = 0.7 × 0.70 − 0.3 × 0.20 = 0.490 − 0.060 = 0.430 ← chosen

d3 ranks second, ahead of the near-duplicate d2, even though d2 is more relevant. The user now sees two genuinely different options: a summary and its detail.

5.9Evaluating rankings

How do we know a ranker is good? Compare its output to human relevance judgments.

Precision and recall at k

Precision@k = relevant items in top k / k Recall@k = relevant items in top k / all relevant items

These metrics ignore order within the top k.

Mean reciprocal rank (MRR)

This measures how high the first relevant item appears, averaged over queries:

MRR = (1 / |queries|) · Σ_q 1 / rank of first relevant item for q

Example: across three queries, the first relevant item appears at ranks 1, 3 and 2.

MRR = (1/1 + 1/3 + 1/2) / 3 = 1.833 / 3 ≈ 0.611

Normalized discounted cumulative gain (nDCG)

nDCG uses graded relevance (0 = irrelevant … 3 = perfect) and discounts items lower in the list:

DCG@k = Σᵢ₌₁ᵏ (2^{relᵢ} − 1) / log₂(i + 1) nDCG@k = DCG@k / IDCG@k (IDCG = DCG of the ideal ordering; nDCG ∈ [0, 1])

Example: the system returns relevance grades [2, 3, 0]. The ideal order is [3, 2, 0].

DCG = (2² − 1)/log₂2 + (2³ − 1)/log₂3 + 0 = 3/1 + 7/1.585 ≈ 3.000 + 4.417 = 7.417 IDCG = (2³ − 1)/log₂2 + (2² − 1)/log₂3 + 0 = 7/1 + 3/1.585 ≈ 7.000 + 1.893 = 8.893 nDCG@3 = 7.417 / 8.893 ≈ 0.834

Putting the second-best item first costs about 17% of the ideal score. The exponential gain (2rel − 1) means that misplacing the best item hurts most.

nDCG gives big credit for putting great results near the top and shrinking credit for results further down. It then divides by the best score that was possible, so 1.0 means “perfect order”.

5.10Putting it together: the candidate score

For each candidate plan π (sources, joins, field matches, filters), combine everything from this module into one score:

log Score(π) = Σ_{(s,f) ∈ M*} log P(f represents s) ← field matching (5.2) + Σ_values log P(value valid in field) ← value validation (5.3) + Σ_stages log pᵢ ← stage confidence (5.4) + log Consistency(A_π) + log P(correct | checks) ← sanity checks (5.5) + log r(Q, sources of π) ← retrieval rank (5.6–5.7)

The candidates are then ordered by score and diversified with MMR (5.8). The leading candidates go to Module 6, which selects the final answer.

Key takeaways

  • Field matching is a global assignment problem. The Hungarian algorithm beats greedy picking, and log-probability weights turn it into joint probability.
  • Validate every value against the data, and infer unknown columns with Bayes’ rule. An empty result means a filter is wrong.
  • Confidence compounds: multiply across stages, and ask about the weakest link.
  • Sanity checks are evidence. A failed check can rightly collapse confidence through Bayes’ rule.
  • Retrieval runs in two stages: recall first (errors there are permanent), then precision.
  • Learning to rank should optimize order, through pairwise or listwise objectives.
  • MMR keeps near-duplicates from crowding the top, and nDCG and MRR judge rankings by order, not just membership.
