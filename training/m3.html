3.1The problem: the question doesn’t say how things connect

Consider: “What was revenue by product category for customers in each region?” The user named four concepts (Revenue, ProductCategory, Customer, Region) but said nothing about:

  • Which tables hold them
  • How those tables link together
  • What time period is meant
  • Whether test accounts or cancelled orders count

Modules 1 and 2 found the right sources and concepts. This module covers the hidden structure between them.

We split “implicit” into two kinds:

KindQuestionTools
StructuralHow do these entities connect?Schema graphs, join evidence, shortest paths, Steiner trees
ContextualWhat constraints did the user assume?Latent variables, priors, decision rules

The sentence tells us what to calculate, but often not the database route or quiet assumptions behind it. We infer both, then make uncertain choices visible.

Like planning a trip from a list of destinations, we need both a road map (the joins) and the traveler’s preferences (time window and exclusions) before choosing a route.

H = (V, E, w) V = entities / tables e.g. Customers, Orders, OrderLines, Products, Regions E = candidate links pairs of columns that could join w : E → ℝ≥0 cost of using a link (low = trustworthy)
H
H is the weighted schema graph: the map of tables and possible joins. Customers, Orders and Products are nodes in H.
V
V is the set of database entities or tables. V includes Customers and OrderLines.
E
E is the set of candidate links between columns that might join. Customers.customer_id to Orders.cust_id is a candidate edge.
w

→
The arrow means “maps each link to a cost.” Each e in E is mapped to w(e).

3.3Evidence that two columns join

Column names are a weak hint. cust_id and customer_id look related, but so do id and id in unrelated tables. Stronger evidence comes from values.

Let V(x) be the set of distinct values in column x.

Signal 1: Containment (inclusion dependency)

What fraction of x’s values appear in y?

contain(x ⊆ y) = |V(x) ∩ V(y)| / |V(x)|
contain(x ⊆ y)
This directional score is the fraction of x’s distinct values present in y; it ranges from 0 to 1. Orders.cust_id has 940 of 950 values in Customers.customer_id.
x
x is the source column whose values are checked against y. x can be Orders.cust_id.
y
y is the comparison column that may contain x’s values. y can be Customers.customer_id.
V(x), V(y)
V(x) and V(y) are the sets of distinct values in columns x and y. V(x) contains 950 distinct IDs.
|…|
Vertical bars mean “number of items in this set.” |V(x)| = 950.
∩
The intersection keeps only values appearing in both sets. |V(x) ∩ V(y)| = 940.
/
Division converts the match count into a fraction of x. 940 / 950 ≈ 0.989.

This measure is asymmetric. A foreign key x points to a primary key y when nearly all x values exist in y, even if y has extra values.

Signal 2: Jaccard similarity

J(x, y) = |V(x) ∩ V(y)| / |V(x) ∪ V(y)|
J(x, y)
J is Jaccard similarity: shared distinct values divided by values in either set; range 0–1. J = 940 / 1,010 ≈ 0.931.
∪
The union combines both sets and counts shared values once. |V(x) ∪ V(y)| = 1,010.
|…|
Vertical bars mean the number of distinct values in the set. The intersection has 940 values.
/
Division gives the fraction of the combined set that is shared. 940 shared values / 1,010 total.

This measure is symmetric. It is lower when one side has many extra values, so containment is usually more informative for joins.

Signal 3: Uniqueness (key-ness)

uniq(y) = distinct values in y / rows in y (1.0 = every value is unique)
uniq(y)
uniq is distinct values divided by rows; 1 means unique, while a lower value means duplicates. A unique customer_id column has uniq = 1.0.
distinct values in y
The numerator counts different values in y, not rows. Customers.customer_id has 1,000 distinct values.
rows in y
The denominator counts all records in y. The example uses 1,000 rows.
1.0
1.0 is the maximum uniqueness score: every row has a different value. uniq(Customers.customer_id) = 1.0.

When one side is unique, the join is many-to-one: safe for looking up attributes.

Signal 4: Name similarity

Edit distance or embedding similarity of column names (Module 2), after normalization.

Containment asks “does every child key have a parent?” Jaccard asks “how much do the two sets overlap overall?” A good foreign key can have high containment but modest Jaccard when the parent has many unused rows.

Combining the signals: logistic model

P(valid join | x, y) = σ(z) = 1 / (1 + e^(−z)) z = θ₀ + θ₁·name_sim + θ₂·contain(x ⊆ y) + θ₃·uniq(y)
P(valid join | x, y)
P means probability, from 0 to 1; the vertical bar means “given.” This is the chance x and y form a valid join. For the real candidate, P is about 0.987.
x, y
x and y are the two candidate columns being tested. Orders.cust_id and Customers.customer_id.
σ(z)
σ is the logistic function that turns any real score z into a probability between 0 and 1. σ(4.356) ≈ 0.987.
1
The 1 in the denominator fixes the logistic curve’s scale. 1 + 0.0128 is the example denominator.
e
e is Euler’s number, about 2.718; raising it to −z makes large positive z yield a high probability. e^(−4.356) ≈ 0.0128.
z
z is the combined evidence score before converting it to a probability. The real candidate has z = 4.356.
θ₀
θ₀ is the baseline score when evidence signals are zero; increasing it raises the predicted probability. The illustrative baseline is −4.
θ₁, θ₂, θ₃
These are learned weights for name similarity, containment, and uniqueness; a larger positive weight makes that signal affect z more. Illustrative weights are 3, 4, and 2.
name_sim
name_sim measures similarity between the two column names, usually from 0 to 1. The real candidate scores 0.8.
contain(x ⊆ y)
Containment measures how much of x’s values appear in y, from 0 to 1. The real candidate scores 0.989.
uniq(y)
Uniqueness measures the share of y rows with distinct values, from 0 to 1. Customers.customer_id scores 1.0.
+
Addition combines the baseline and weighted evidence signals. −4 + 2.4 + 3.956 + 2 = 4.356.
·
The dot means multiplication of each signal by its weight. 4 · 0.989 = 3.956.
−z
The minus sign reverses the score in the logistic exponent. For z = 4.356, the exponent is −4.356.

Illustrative weights: θ₀ = −4, θ₁ = 3, θ₂ = 4, θ₃ = 2.

3.4Why edge cost = −log P

We want the most probable chain of joins. If the joins are independent, a path’s probability is the product of its edge probabilities:

P(path valid) = Π_{e ∈ path} P(e)
P(path valid)
This is the probability every link in the chosen path is a valid join; it is between 0 and 1. A path with total cost 0.30 has probability about 0.74.
Π
Π means multiply the indicated probabilities together. For two edges with probabilities 0.9 and 0.8, multiply 0.9 × 0.8.
e ∈ path
e is one edge, and “is included in”; the product covers every edge in the path. The Customers → Orders → OrderLines path has multiple edges.
P(e)
P(e) is the estimated probability that edge e is a valid join. An edge with cost 0.05 is highly trusted.

Taking −log turns products into sums, and maximization into minimization:

argmax_path Π P(e) = argmin_path Σ −log P(e)
argmax
argmax means “choose the option that makes the following value largest.” Choose the path with the highest join probability.
argmin
argmin means “choose the option that makes the following value smallest.” Choose the path with the lowest total cost.
path
A path is a connected sequence of table-to-table joins. Customers → Orders → OrderLines.
Π P(e)
Multiply each edge’s join probability to get the whole path’s probability. 0.9 × 0.8 = 0.72 for a two-edge path.
Σ
Σ means add the value for every edge in the path. Add each edge cost to get total path cost.
e
e is one candidate join edge in the path. Customers to Orders is one edge.
−log P(e)
Take the negative logarithm of an edge probability; high-confidence edges then have low cost. If P(e) is near 1, −log P(e) is near 0.
=
The equality says maximizing a product of probabilities is equivalent to minimizing summed negative log probabilities. The best-probability path is the lowest-cost path.

So defining cost(e) = −ln P(e) means that shortest path = most probable path, and standard graph algorithms apply directly.

3.5Finding the best join path

Via Orders: “products customers bought.” Via SupportTickets: “products customers complained about.”

Dijkstra’s algorithm (intuition)

Grow outward from the start node, always expanding the cheapest frontier node first. The first time the target is reached, the cost found is the cheapest possible.

dist[start] = 0; dist[others] = ∞ repeat: u ← unvisited node with smallest dist for each neighbour v of u: dist[v] ← min( dist[v], dist[u] + w(u, v) ) until target visited
dist[start]
dist stores the best-known total cost from the starting node; it begins at zero. dist[Customers] = 0.
dist[others]
Every other node initially has infinite cost because no route has been found yet. dist[Products] = ∞ at the start.
u
u is the unvisited node currently chosen because it has the smallest known distance. The next u is the closest unvisited table.
v
v is a neighbour of u connected by one candidate join. Orders can be a neighbour of Customers.
dist[v]
dist[v] is the best route cost currently known from start to v. Update the best known cost to Products.
min(a, b)
min keeps the smaller of the old route and a newly discovered route. Keep the shorter of dist[v] and dist[u] + w(u,v).
w(u, v)
w(u,v) is the non-negative cost of the candidate edge from u to v. A trustworthy join may have cost 0.05.
+
Addition combines the route to u with the next edge cost. dist[u] + 0.05 extends a path by one join.
←
The arrow means “replace the current value with.” Set dist[v] to the smaller candidate cost.
∞
Infinity means no route is known yet. Unvisited nodes start at ∞.
repeat / until
Keep selecting and updating nodes until the target node is visited. Stop once Products is reached.

Using the graph in 3.2:

Paths carry meaning

Both paths are valid joins, but they answer different questions:

Purchase route

Customers → Orders → OrderLines → Products

Products customers bought.

Support route

Customers → SupportTickets → Products

Products customers complained about.

So path choice is also a semantic decision. Combine graph cost with fit to the question’s intent:

score(path) = −cost(path) + λ · sim( concepts on path, C(Q) )
score(path)
This score balances low join cost against how well the path matches the question’s meaning. A revenue question favors the path through OrderLines.
cost(path)
cost is the sum of the join costs along the path; lower is better. The Customers→Orders→OrderLines→Products path costs 0.30.
λ
λ (lambda) controls how strongly semantic fit influences the path score; raising it favors meaning match over join cost. For a revenue question, a larger λ can favor OrderLines.
sim
sim measures similarity between concepts on the path and the concepts asked about, typically 0–1. A path containing the revenue concept has stronger similarity.
concepts on path
These are the business concepts represented by the tables and joins in the path. OrderLines represents revenue-bearing purchases.
C(Q)
C(Q) is the set of concepts recognized in question Q. Q asking about revenue includes the revenue concept.
−
Subtracting path cost penalizes expensive or less-trusted joins. A cost of 0.30 lowers the score by 0.30.
·
Multiplication makes semantic similarity count according to λ. λ · sim adds a weighted meaning bonus.

“Revenue” lives on OrderLines, so the purchase path gains a further bonus.

When to ask

ratio = P(best path) / P(second-best path) if ratio < ρ (e.g. 1.5) → paths are comparably plausible: clarify or state the choice
ratio
ratio compares the best path’s probability with the runner-up’s; values near 1 mean they are similarly plausible. 0.82 / 0.61 ≈ 1.34.
P(best path)
This is the probability assigned to the highest-ranked path. The example best path has probability 0.82.
P(second-best path)
This is the probability assigned to the runner-up path. The second-best path has probability 0.61.
ρ
ρ (rho) is a user-set ambiguity threshold; raising it causes more close choices to trigger clarification. With ρ = 1.5, a ratio of 1.34 calls for clarification.
<
“Less than”; when the ratio falls below ρ, the paths are close enough to ask the user. 1.34 < 1.5.
→
The arrow means the condition leads to this action. A low ratio leads to clarifying or stating the choice.

Here 0.82 / 0.61 ≈ 1.34. On graph cost alone that falls under ρ, but the semantic bonus from “revenue” resolves it.

The mathematically cheapest path is only a structural candidate. Use user intent to decide what the path means; if paths remain close, clarify or disclose the choice.

3.6Connecting many entities: Steiner trees

Our question needs four entities connected at once: {Regions, Customers, OrderLines, Products}. Joining pairs one at a time can produce redundant or conflicting paths. Instead, find the cheapest tree that touches every required node:

T* = argmin_{T ⊆ H, T connects all terminals} Σ_{e ∈ T} w(e)
T*
T* is the selected minimum-cost tree connecting all required entities; * marks the chosen solution. The tree can connect Regions, Products and SupportTickets.
argmin
Choose the candidate tree with the smallest total cost. Select the cheapest tree that connects all terminals.
T ⊆ H
T is a subset of graph H: the chosen edges and nodes come from the schema graph. T uses links already present in H.
terminals
Terminals are the required tables that the question needs connected. Regions, Products and SupportTickets can be required terminals.
Σ
Add the cost of every edge included in T. Sum all selected join costs.
e ∈ T
e is an edge included in the chosen tree. Customers→Orders is one selected edge.
w(e)
w(e) is the cost of using edge e; lower means more trustworthy. An edge can have cost 0.05.
connects all terminals
The chosen tree must provide a connected route among every required table. All three requested entities must be reachable.

The exact Steiner tree problem is NP-hard.

Approximation: compute shortest paths between every pair of terminals, build a minimum spanning tree over those distances, then expand it back into real edges. This is guaranteed to be within 2× the optimum, and usually much closer.

This is the Steiner tree problem. The tree may include extra “connector” nodes, such as Orders here, which the user never mentioned.

Solution for the example

Regions ─0.10─ Customers ─0.05─ Orders ─0.05─ OrderLines ─0.10─ Products

Total cost = 0.30 ⇒ P(all joins valid) ≈ e^(−0.30) ≈ 0.74
Total cost
Total cost is the sum of selected join costs; it is non-negative. The example tree costs 0.30.
P(all joins valid)
This is the chance all joins in the chosen plan are correct, estimated from their costs. For total cost 0.30, the estimate is about 0.74.
e^(−0.30)
Convert the negative total cost back to a probability using Euler’s number. e^(−0.30) ≈ 0.74.
≈
“Approximately equal”; the probability is rounded. 0.74 is an approximate value.

Orders is a Steiner node: it is required for connectivity, even though the question never names it.

Complexity

The exact optimization is NP-hard; the shortest-path/MST expansion is a practical approximation with a 2× guarantee.

Think of connecting several homes to a road network: the cheapest solution may share a road and pass through a junction no homeowner named.

3.7Join traps: when correct joins give wrong numbers

A join can be valid and still inflate results. This is one of the most common silent errors in business analytics.

Fan-out

Let order o have amount aₒ and match mₒ rows in a joined table.

SUM over joined rows = Σₒ aₒ · mₒ correct total = Σₒ aₒ
Σₒ
Sum once over each original order o, before row-multiplying joins. There are three original orders.
aₒ
aₒ is the measure value belonging to original order o, such as its amount. An order amount can be $100.
mₒ
mₒ is how many joined rows repeat order o after the join. If an order matches 3 shipment rows, mₒ = 3.
SUM over joined rows
A naive sum adds the repeated measure once for every joined copy. $100 repeated 3 times becomes an incorrect $300.
correct total
The correct total adds each original order amount once. Three orders are summed once each.
·
Multiplication shows the amount is repeated mₒ times. $100 × 3 rows = $300.
mₒ = 1
This condition means each order appears exactly once in joined rows. Only then is the naive joined SUM safe.

This is correct only if every mₒ = 1.

Example: order #1 is worth $100 and has 3 shipment rows. After the join, the sum reports $300.

Chasm trap

Here one parent has two independent one-to-many children.

A customer has 3 orders and 2 support tickets. Joining both onto the customer produces 3 × 2 = 6 rows:

COUNT(orders) after join = 6 (true value: 3) COUNT(tickets) after join = 6 (true value: 2) In general, a parent with k₁ and k₂ children produces k₁ · k₂ rows.
COUNT(orders)
COUNT counts order rows remaining after the join; duplicate rows inflate it. The joined result counts 6, but the true count is 3.
COUNT(tickets)
COUNT counts ticket rows after joining; duplicated combinations inflate it too. The joined result counts 6, but true tickets are 2.
k₁, k₂
k₁ and k₂ are the number of child rows of each of two child tables for one parent. The example parent has 3 orders and 2 tickets.
k₁ · k₂
Multiply child counts to find the combined rows created by joining both children. 3 × 2 = 6 rows.
true value
The true count is measured before unrelated child tables multiply one another. 3 orders and 2 tickets, not 6 of each.

Independent child collections multiply rows when joined together.

Detection and fixes

fan-out factor F = rows after join / rows before join F > 1 on the table that holds the measure ⇒ inflation risk
F
F is the fan-out factor: joined row count divided by the starting row count; greater than 1 signals expansion. If 3 rows become 6, F = 2.
rows after join
Count the result rows after applying the join. Three orders and two tickets can create six combinations.
rows before join
Count rows in the measure’s original table before joining. The measure may start with 3 order rows.
> 1
Greater than one means each original row expanded into multiple rows. F = 2 indicates inflation risk.
→
This arrow means the condition implies the warning. Fan-out on the measure implies aggregation risk.
FixIdea
Aggregate first, then joinSum each child to the parent grain before joining
Count distinctCOUNT(DISTINCT order_id) instead of COUNT(*)
Respect grainOnly join up (many-to-one) from the measure’s table

Rule of thumb: a measure should only travel along many-to-one edges. The uniqueness signal from 3.3 tells you which direction that is.

A join can be semantically correct yet analytically unsafe. Before summing or counting, check how many joined rows each measure row produces.

3.8Hidden hierarchies: functional dependencies

Some relationships live inside a table, such as City → Region → Country. If each city belongs to exactly one region, then region is a function of city, and the system can roll up from city to region safely.

Measuring it with conditional entropy

H(Y | X) = Σₓ P(x) · H(Y | X = x) H(Y | X) = 0 ⟺ X → Y is a perfect functional dependency
H(Y | X)
H is conditional entropy: the remaining uncertainty about Y after knowing X; measured in bits. H(Region | City) ≈ 0.459 bits.
Y
Y is the value being predicted or explained. Y can be Region.
X
X is the value used to predict Y. X can be City.
Σₓ
Average across every possible value x of X, weighted by its probability. Paris, Lyon and Austin contribute to the average.
P(x)
P(x) is the chance of seeing X=x, between 0 and 1. P(Austin) = 3/6.
H(Y | X = x)
This is the uncertainty in Y within the group whose X value is x. H(Region | Austin) ≈ 0.918 bits.
= 0
Zero conditional entropy means X determines Y exactly in these data. Each city having only one region gives H = 0.
⇔
This means “if and only if”: either statement describes the same perfect relationship. Zero entropy matches a perfect dependency.
X → Y
The arrow means X functionally determines Y: each X value has exactly one Y value. City → Region when every city maps to one region.

A normalized version, the uncertainty coefficient:

U(Y | X) = 1 − H(Y | X) / H(Y) (1 = perfect dependency, 0 = independent)
U(Y | X)
U is the uncertainty coefficient: the fraction of Y’s uncertainty removed by knowing X; typically 0–1. U(Region | City) = 0.50.
1
The leading 1 represents all of Y’s original uncertainty before X is known. Start with 1.0, or 100%.
H(Y | X)
Uncertainty in Y that remains after X is known. The example has 0.459 bits remaining.
H(Y)
Total uncertainty in Y before learning X. Region has 0.918 bits of uncertainty.
/
Divide remaining uncertainty by total uncertainty to get the remaining fraction. 0.459 / 0.918 = 0.50.
0
U = 0 means X gives no reduction in uncertainty about Y. Independent values have U near 0.
1
U = 1 means knowing X removes all uncertainty about Y. A perfect dependency has U = 1.

A simpler count-based alternative: g₃ = the fraction of rows that must be removed to make the dependency exact.

Overall uncertainty in Region without knowing City. Four EU and two NA rows give about 0.918 bits.
2/6, 1/6, 3/6
These weights are the fractions of all six rows in each city group. Paris 2/6, Lyon 1/6, Austin 3/6.
4/6, 2/6
These are the overall proportions of EU and NA rows. 4 EU and 2 NA among 6 rows.
U
U is the uncertainty coefficient, showing how much city reduces uncertainty about region. U = 1 − 0.459/0.918 = 0.50.
g₃
g₃ is the fraction of rows that must be removed to make the dependency exact; lower is better. Removing one of six rows gives g₃ = 1/6 ≈ 0.17.
→
The arrow means that removing the stated row leads to a perfect dependency. Remove Austin’s inconsistent row.
≈
“Approximately equal”; decimal values are rounded. 0.918 is rounded.

Interpretation: the two metrics disagree in tone. Entropy looks weak at 0.50, because tiny samples magnify a single error. g₃ shows the dependency holds for 83% of rows, and the violation is one dirty record. In practice, a dependency with small g₃ suggests “use the hierarchy, and flag the data-quality issue.”

3.9Contextual inference: what the user didn’t say

Unstated constraints are latent variables z. We infer them the same way we inferred concepts:

z* = argmax_z P(z | Q, 𝒪 ) ∝ P(Q | z) · P(z | intent, ontology)
z*
z* is the most likely inferred hidden constraint; * means the selected best option. The best time-window hypothesis may be “last 12 months.”
argmax_z
Choose the constraint z with the largest posterior probability. Compare year-to-date and last-12-month options.
P(z | Q, ontology)
Posterior probability of constraint z given user question Q and ontology. The question and business rules make one time window more likely.
Q
Q is the user’s natural-language question. “How has revenue been trending?”
ontology
Ontology is the business rulebook describing concepts and curated constraints. It can record that revenue excludes test accounts.
∝
“Is proportional to”; the right side supplies a score that is normalized into probabilities. Higher likelihood and prior make z more probable.
P(Q | z)
Likelihood: how well candidate constraint z would explain the wording of Q. A trend question fits a time-window constraint.
P(z | intent, ontology)
Prior probability of z given the question’s intent and business rules. The ontology favors excluding test accounts.
·
Multiply the likelihood by the prior to combine evidence. A strong question fit and rule prior reinforce one another.

Example 1: a standard exclusion

The ontology records a curated rule that business metrics exclude test accounts:

P(exclude_test = true | metric = Revenue, curated rule) ≈ 0.95
P(exclude_test = true | metric = Revenue, curated rule)

exclude_test = true

metric = Revenue
This condition says the requested measure is Revenue. A Revenue question matches the rule.
curated rule
A reviewed business rule recorded in the ontology, not a guessed user preference. Revenue excludes test accounts.
≈ 0.95
About a 95% probability or confidence, not certainty. The curated rule is estimated at 0.95.

Apply the rule by default and mention it.

“How has revenue been trending?” The intent is a trend (more in Module 4).

P(z₁) = 0.50 < τ = 0.6 ⇒ not confident enough to apply silently

Probability of the first candidate hidden constraint. The candidate has probability 0.50.
z₁
z₁ is one candidate assumption, with subscript 1 marking the first option. One possible time window is year to date.

τ (tau) is the minimum confidence threshold for silently applying a constraint; raising it makes silent action less common. The lesson uses τ = 0.6.
0.50
The candidate probability is one half, or 50%. P(z₁) = 0.50.
0.6
The threshold is 60%; a 50% candidate falls short. 0.50 < 0.6.
<
Less than means confidence is below the action threshold. 0.50 is below τ.

The arrow means the low-confidence result leads to asking or stating an assumption. Do not apply the choice silently.

Decision theory view

Choose the constraint that minimizes expected loss:

z* = argmin_z Σ_{z'} P(z' | Q) · Loss(z, z')
z*
z* is the action or constraint with the lowest expected loss. Choose the safer time window when mistakes have unequal costs.
argmin_z
Choose the candidate z that makes expected loss smallest. Compare each possible time-window choice.
Σ over z′
Add expected loss over every possible true constraint z′. Include both year to date and last 12 months
z₁
z₁ is a possible actual constraint; the prime distinguishes it from the chosen action z. z₁ may be the user’s intended time window.
P(z₁ | Q)
Probability that z′ is intended, given the user’s question. The question assigns probabilities to candidate windows.
Loss(z, z₁)
Loss is the cost of choosing z when the intended constraint is z₁. Silently excluding valid revenue may cost more than including test rows.
·
Multiply each possible outcome’s probability by its loss. A 0.5 chance times a large loss weighs heavily.
0/1 loss
A simple loss is 0 for a correct choice and 1 for an incorrect one. With 0/1 loss, choose the most probable z.

With 0/1 loss, this reduces to “pick the most probable z”. With asymmetric loss, for example when silently including test data is far worse than excluding it, the choice can move away from the most probable option toward the safest one.

Explicit constraints always win

if the user states constraint κ explicitly: P(κ) = 1, override every prior
κ
κ (kappa) names a constraint the user explicitly stated. an instruction to exclude test accounts is an explicit constraint.
P(κ) = 1
An explicit instruction is treated as certain for this decision. The stated constraint gets probability 1.
prior
A prior is the default belief before considering an explicit user instruction. A curated rule is a prior, not a replacement for the user’s words.
=
Equality here means the explicit constraint is enforced, not merely considered likely. P(κ) equals 1.

Priors only fill gaps. They never overwrite what the user actually said.

3.10Combining weak evidence

Relationships are often supported by several imperfect clues.

Chains (all links must hold): multiply

(A R₁ B) ∧ (B R₂ C) ⇒ A ~ C with conf = conf(R₁) · conf(R₂)
A, B, C
A, B and C are entities or concepts connected by two relations. A customer connects to an order, which connects to an order line.
R₁, R₂
R₁ and R₂ are relation links; subscript 1 is the first hop and 2 the next. Customer→Order is R₁; Order→OrderLine is R₂.
∧
∧ means both links in the chain must hold. Both R₁ and R₂ must be valid.
→
The arrow means the two links support a derived relationship between A and C. A can be related to C through B.
~
The tilde means “is related to,” not necessarily a direct database key. Customer ~ OrderLine through Orders.
conf
conf is confidence in a relation, a value from 0 to 1. A two-hop chain may have confidence 0.72.
conf(R₁), conf(R₂)
These are the confidence values of the first and second links. 0.9 and 0.8.
·
Multiply link confidences because every link in the chain must work. 0.9 × 0.8 = 0.72.

For example, 0.9 × 0.8 = 0.72. Confidence shrinks with every hop, which is why long inferred chains deserve scepticism.

Independent clues (any one suffices): noisy-OR

P(related) = 1 − Πᵢ (1 − pᵢ)
P(related)
Probability that at least one independent clue supports the relationship, from 0 to 1. Two clues with probabilities 0.6 and 0.5 yield 0.80.
Πᵢ
Multiply across clue index i; each clue contributes its own failure chance. Use clue 1 and clue 2.
i
i indexes each separate, independent clue. i=1 can be name match; i=2 value overlap.
pᵢ
pᵢ is the probability supplied by clue i, between 0 and 1. pᵢ = 0.6 and pᵢ = 0.5.
(1 − pᵢ)
This is the chance clue i does not support the relationship. For pᵢ = 0.6, failure chance is 0.4.
1 − Πᵢ(1 − pᵢ)
Subtract the chance that every clue fails from 1 to get the chance at least one succeeds. 1 − (0.4 · 0.5) = 0.80.
−
Subtraction converts failure probability into success probability. 1 − 0.20 = 0.80.

Example: a name match (0.6) and a value overlap (0.5) independently suggest the same link.

P = 1 − (1 − 0.6)(1 − 0.5) = 1 − 0.4 · 0.5 = 0.80
P
P is the combined probability that the relationship is real, from 0 to 1. The combined result is 0.80.
0.6, 0.5
These are illustrative independent clue probabilities: name match and value overlap. The lesson uses 0.6 and 0.5.
1 − p
For each clue, this is the chance that clue does not support the link. 1 − 0.6 = 0.4; 1 − 0.5 = 0.5.
·
Multiply the independent failure chances, then subtract from 1. 1 − (0.4 · 0.5) = 0.80.
=, ≈
Equals gives exact arithmetic; ≈ marks a rounded approximation. The result is 0.80.

Independent clues reinforce each other, while chained clues dilute.

StructureCombinationEffect of adding evidence
Series (AND)ProductConfidence ↓
Parallel (OR)Noisy-ORConfidence ↑

A chain is a relay race: every handoff must succeed, so one weak handoff lowers the whole chance. Parallel clues are independent witnesses: any one can support the claim, so additional witnesses raise confidence.

3.11Putting it together: scoring a query plan

A complete plan π fixes the sources, joins, roll-ups and filters. Its overall score combines everything in this module:

log Score(π) = Σ_{e ∈ Steiner tree} log P(e) ← join validity (3.3–3.6) + λ₁ · sim( path concepts, C(Q) ) ← path meaning (3.5) − λ₂ · 1[fan-out on the measure] ← trap penalty (3.7) + Σ_{FDs used} log(1 − g₃) ← hierarchy soundness (3.8) + Σ_{latent z} log P(z* | Q, 𝒪 ) ← assumed constraints (3.9)
log Score(π)
This is the logarithm of the overall plan score; higher is better, and summing logs combines evidence. π* is selected by maximizing log Score(π).
π
π is one candidate query/join plan. A plan can connect Region, Product and Revenue.
Σ_{e ∈ Steiner tree}
Add one term for each selected edge e in the connecting tree. The tree includes the joins through Orders.
e
e is a join edge used by the plan. Customers→Orders is one edge.
Steiner tree
The Steiner tree is the low-cost set of joins connecting all requested tables, possibly through extra tables. Orders can connect Customers to OrderLines.
log P(e)
Log probability rewards joins that are likely valid; higher P(e) gives a less negative term. A high-confidence join contributes a better score.
λ₁
λ₁ controls the reward for matching question meaning; larger values favor semantically relevant paths. A revenue question rewards the OrderLines path.
sim(path concepts, C(Q))
Similarity between concepts along the plan and concepts in question Q, usually 0–1. OrderLines matches the revenue concept.
C(Q)
The concepts extracted from question Q. Revenue is a concept in the worked question.
λ₂
λ₂ controls the penalty for fan-out on the measured data; larger values penalize unsafe plans more. A high λ₂ discourages duplicating order amounts.
1[condition]
The bracketed indicator is 1 when the condition is true and 0 otherwise. 1[fan-out on the measure] is 1 when joins duplicate the measure.
fan-out on the measure
A join expands rows of the table carrying the value being summed or counted. Repeated order rows can inflate revenue.
Σ_{FDs used}
Add a term for every functional dependency used by the plan. City→Region is one dependency.
FD
FD means functional dependency: one field determines another. City determines Region when each city has one region.
g₃
g₃ is the fraction of rows removed to make an FD exact; a smaller value means stronger evidence. Removing 1 of 6 rows gives g₃ ≈ 0.17.
log(1 − g₃)
This rewards dependable hierarchies; when g₃ is small, 1−g₃ is near 1. For g₃ ≈ 0.17, the dependency fits 5/6 rows.
Σ_{latent z}
Add a term for each inferred but unstated constraint. A time window is one latent constraint.
z*
z* is the selected most likely constraint. “Last 12 months” can be the chosen window.
P(z* | Q, ontology)
Probability the chosen constraint applies, given the question and ontology. The curated Revenue exclusion has confidence about 0.95.
ontology
Ontology is the business ontology containing concepts and curated rules. It records the test-account exclusion.
+, −
Add favorable evidence; subtract the fan-out risk penalty. Join fit and semantic fit add, unsafe fan-out subtracts.
The best plan is π* = argmax log Score(π).
π*
π* is the chosen best plan; * marks the selected option. It is the plan with the highest log score.
argmax
Choose the candidate plan that makes the score largest. Compare the plausible join plans.
log Score(π)
The plan score combines join confidence, question fit, safe aggregation, hierarchy quality and assumptions. A good plan connects the requested tables without inflating Revenue.

Every assumption made along the way is surfaced to the user.

Join validity, semantic fit, safe aggregation, hierarchy quality and contextual assumptions all contribute; a strong plan must survive each check.

Check your understanding

  1. Compute: a path has edges with P = 0.9 and P = 0.8. What are its total cost and its probability?Cost = −ln 0.9 − ln 0.8 ≈ 0.105 + 0.223 = 0.328. Probability = 0.9 × 0.8 = 0.72 (equivalently, e^(−0.328) ≈ 0.72).
  2. Compute: column A has 200 distinct values, B has 500, and they share 180. What are contain(A ⊆ B) and Jaccard? Which column is more likely the foreign key?contain = 180 / 200 = 0.90. Jaccard = 180 / (200 + 500 − 180) = 180 / 520 ≈ 0.346. A is likely the foreign key pointing to B: most of A’s values live in B, while B has many extra values.
  3. Compute: an order worth $50 joins to 4 line-item rows. What does a naive SUM report?$50 × 4 = $200, inflated by a fan-out factor of 4.
  4. Compute: two independent clues suggest a link with P = 0.7 and P = 0.4. What is the combined noisy-OR probability?1 − (0.3)(0.6) = 1 − 0.18 = 0.82.
  5. Reason: why must edge cost be −log P rather than 1 − P for shortest-path search to find the most probable path?Path probability is a product of edge probabilities. Only −log converts that product into a sum, so minimizing summed cost is the same as maximizing probability. Sums of (1 − P) have no such correspondence.
  6. Reason: a user asks “revenue last quarter, including test accounts”. What happens to the curated exclusion rule?The explicit constraint gets P = 1 and overrides the curated default. Priors fill gaps; they never contradict what the user stated.

Key takeaways

  • Data landscapes are graphs. Joins are edges with cost −log P(valid), so the shortest path is the most probable path.
  • Containment plus uniqueness beat column names as join evidence.
  • Steiner trees connect many entities at once, often through nodes the user never mentioned.
  • Valid joins can still give wrong numbers: watch for fan-out and chasm traps, and let measures travel only many-to-one.
  • Conditional entropy and g₃ reveal hidden hierarchies and their data-quality issues.
  • Unstated constraints are latent variables: fill gaps with priors, surface uncertain assumptions, and never override explicit instructions.
  • Evidence in series dilutes confidence, while evidence in parallel reinforces it.
