3.1The problem: the question doesn’t say how things connect

Consider: “What was revenue by product category for customers in each region?” The user named four concepts (Revenue, ProductCategory, Customer, Region) but said nothing about:

  • Which tables hold them
  • How those tables link together
  • What time period is meant
  • Whether test accounts or cancelled orders count

Modules 1 and 2 found the right sources and concepts. This module covers the hidden structure between them.

We split “implicit” into two kinds:

KindQuestionTools
StructuralHow do these entities connect?Schema graphs, join evidence, shortest paths, Steiner trees
ContextualWhat constraints did the user assume?Latent variables, priors, decision rules

The sentence tells us what to calculate, but often not the database route or quiet assumptions behind it. We infer both, then make uncertain choices visible.

Like planning a trip from a list of destinations, we need both a road map (the joins) and the traveler’s preferences (time window and exclusions) before choosing a route.

3.2The schema graph

Definition

H = (V, E, w) V = entities / tables e.g. Customers, Orders, OrderLines, Products, Regions E = candidate links pairs of columns that could join w : E → ℝ≥0 cost of using a link (low = trustworthy)

Example landscape

Orders has 950 distinct cust_id values, and Customers has 1,000 distinct customer_id values. They share 940:

contain = 940 / 950 ≈ 0.989 Jaccard = 940 / (950 + 1,000 − 940) = 940 / 1,010 ≈ 0.931 uniq(Customers.customer_id) = 1.0 name_sim ≈ 0.8

Each number in the graph is an edge cost. The rest of this module explains where those costs come from and how to use them.

Corrected schema landscape; edge labels are costs.

A schema graph turns “which tables can connect?” into a weighted road map: tables are places, candidate joins are roads, and a low cost means stronger evidence.

3.3Evidence that two columns join

Column names are a weak hint. cust_id and customer_id look related, but so do id and id in unrelated tables. Stronger evidence comes from values.

Let V(x) be the set of distinct values in column x.

Signal 1: Containment (inclusion dependency)

What fraction of x’s values appear in y?

contain(x ⊆ y) = |V(x) ∩ V(y)| / |V(x)|

This measure is asymmetric. A foreign key x points to a primary key y when nearly all x values exist in y, even if y has extra values.

Signal 2: Jaccard similarity

J(x, y) = |V(x) ∩ V(y)| / |V(x) ∪ V(y)|

This measure is symmetric. It is lower when one side has many extra values, so containment is usually more informative for joins.

Signal 3: Uniqueness (key-ness)

uniq(y) = distinct values in y / rows in y (1.0 = every value is unique)

When one side is unique, the join is many-to-one: safe for looking up attributes.

Signal 4: Name similarity

Edit distance or embedding similarity of column names (Module 2), after normalization.

Containment asks “does every child key have a parent?” Jaccard asks “how much do the two sets overlap overall?” A good foreign key can have high containment but modest Jaccard when the parent has many unused rows.

Combining the signals: logistic model

P(valid join | x, y) = σ(z) = 1 / (1 + e^(−z)) z = θ₀ + θ₁·name_sim + θ₂·contain(x ⊆ y) + θ₃·uniq(y)

Illustrative weights: θ₀ = −4, θ₁ = 3, θ₂ = 4, θ₃ = 2.

Worked example: real join vs. coincidence

Candidate A: Orders.cust_id → Customers.customer_id. Corrected extracted values: contain = 0.989, name_sim = 0.8, uniq = 1.0.

z = −4 + 3(0.8) + 4(0.989) + 2(1.0) = −4 + 2.4 + 3.956 + 2 = 4.356 P = 1 / (1 + e^(−4.356)) = 1 / (1 + 0.0128) ≈ 0.987

Candidate B (decoy): Orders.cust_id → Employees.emp_id. Both are integer IDs, so some values overlap by coincidence. name_sim = 0.3, contain = 0.30, uniq = 1.0.

z = −4 + 3(0.3) + 4(0.30) + 2(1.0) = −4 + 0.9 + 1.2 + 2 = 0.1 P = 1 / (1 + e^(−0.1)) = 1 / (1 + 0.905) ≈ 0.525

Lesson: both keys are unique integers, but only one shows near-total containment. Coincidental overlap between ID ranges is the most common source of false joins, which is why containment carries the largest weight.

A high name score or some overlapping values alone is not enough: unrelated integer ID ranges can overlap by chance. Evaluate direction, containment and uniqueness together.

3.4Why edge cost = −log P

We want the most probable chain of joins. If the joins are independent, a path’s probability is the product of its edge probabilities:

P(path valid) = Π_{e ∈ path} P(e)

Taking −log turns products into sums, and maximization into minimization:

argmax_path Π P(e) = argmin_path Σ −log P(e)

So defining cost(e) = −ln P(e) means that shortest path = most probable path, and standard graph algorithms apply directly.

3.5Finding the best join path

Via Orders: “products customers bought.” Via SupportTickets: “products customers complained about.”

Dijkstra’s algorithm (intuition)

Grow outward from the start node, always expanding the cheapest frontier node first. The first time the target is reached, the cost found is the cheapest possible.

dist[start] = 0; dist[others] = ∞ repeat: u ← unvisited node with smallest dist for each neighbour v of u: dist[v] ← min( dist[v], dist[u] + w(u, v) ) until target visited

Worked example: Customers → Products

Using the graph in 3.2:

PathCostP(path) = e^(−cost)
Customers → Orders → OrderLines → Products0.05 + 0.05 + 0.10 = 0.20e^(−0.20) ≈ 0.82
Customers → SupportTickets → Products0.20 + 0.30 = 0.50e^(−0.50) ≈ 0.61

The purchase path wins.

Paths carry meaning

Both paths are valid joins, but they answer different questions:

Purchase route

Customers → Orders → OrderLines → Products

Products customers bought.

Support route

Customers → SupportTickets → Products

Products customers complained about.

So path choice is also a semantic decision. Combine graph cost with fit to the question’s intent:

score(path) = −cost(path) + λ · sim( concepts on path, C(Q) )

“Revenue” lives on OrderLines, so the purchase path gains a further bonus.

When to ask

ratio = P(best path) / P(second-best path) if ratio < ρ (e.g. 1.5) → paths are comparably plausible: clarify or state the choice

Here 0.82 / 0.61 ≈ 1.34. On graph cost alone that falls under ρ, but the semantic bonus from “revenue” resolves it.

The mathematically cheapest path is only a structural candidate. Use user intent to decide what the path means; if paths remain close, clarify or disclose the choice.

3.6Connecting many entities: Steiner trees

Our question needs four entities connected at once: {Regions, Customers, OrderLines, Products}. Joining pairs one at a time can produce redundant or conflicting paths. Instead, find the cheapest tree that touches every required node:

T* = argmin_{T ⊆ H, T connects all terminals} Σ_{e ∈ T} w(e)

The exact Steiner tree problem is NP-hard.

Approximation: compute shortest paths between every pair of terminals, build a minimum spanning tree over those distances, then expand it back into real edges. This is guaranteed to be within 2× the optimum, and usually much closer.

This is the Steiner tree problem. The tree may include extra “connector” nodes, such as Orders here, which the user never mentioned.

Solution for the example

Regions ─0.10─ Customers ─0.05─ Orders ─0.05─ OrderLines ─0.10─ Products

Total cost = 0.30 ⇒ P(all joins valid) ≈ e^(−0.30) ≈ 0.74

Orders is a Steiner node: it is required for connectivity, even though the question never names it.

Complexity

The exact optimization is NP-hard; the shortest-path/MST expansion is a practical approximation with a 2× guarantee.

Think of connecting several homes to a road network: the cheapest solution may share a road and pass through a junction no homeowner named.

3.7Join traps: when correct joins give wrong numbers

A join can be valid and still inflate results. This is one of the most common silent errors in business analytics.

Fan-out

Let order o have amount aₒ and match mₒ rows in a joined table.

SUM over joined rows = Σₒ aₒ · mₒ correct total = Σₒ aₒ

This is correct only if every mₒ = 1.

Example: order #1 is worth $100 and has 3 shipment rows. After the join, the sum reports $300.

Chasm trap

Here one parent has two independent one-to-many children.

A customer has 3 orders and 2 support tickets. Joining both onto the customer produces 3 × 2 = 6 rows:

COUNT(orders) after join = 6 (true value: 3) COUNT(tickets) after join = 6 (true value: 2) In general, a parent with k₁ and k₂ children produces k₁ · k₂ rows.

Independent child collections multiply rows when joined together.

Detection and fixes

fan-out factor F = rows after join / rows before join F > 1 on the table that holds the measure ⇒ inflation risk
FixIdea
Aggregate first, then joinSum each child to the parent grain before joining
Count distinctCOUNT(DISTINCT order_id) instead of COUNT(*)
Respect grainOnly join up (many-to-one) from the measure’s table

Rule of thumb: a measure should only travel along many-to-one edges. The uniqueness signal from 3.3 tells you which direction that is.

A join can be semantically correct yet analytically unsafe. Before summing or counting, check how many joined rows each measure row produces.

3.8Hidden hierarchies: functional dependencies

Some relationships live inside a table, such as City → Region → Country. If each city belongs to exactly one region, then region is a function of city, and the system can roll up from city to region safely.

Measuring it with conditional entropy

H(Y | X) = Σₓ P(x) · H(Y | X = x) H(Y | X) = 0 ⟺ X → Y is a perfect functional dependency

A normalized version, the uncertainty coefficient:

U(Y | X) = 1 − H(Y | X) / H(Y) (1 = perfect dependency, 0 = independent)

A simpler count-based alternative: g₃ = the fraction of rows that must be removed to make the dependency exact.

Worked example

H(Region | Paris) = 0 (always EU) H(Region | Lyon) = 0 H(Region | Austin) = −(⅔ log₂ ⅔ + ⅓ log₂ ⅓) ≈ 0.918 bits H(Region | City) = (2/6)(0) + (1/6)(0) + (3/6)(0.918) ≈ 0.459 bits H(Region) = −(4/6 log₂ 4/6 + 2/6 log₂ 2/6) ≈ 0.918 bits U = 1 − 0.459 / 0.918 = 0.50 g₃ = 1/6 ≈ 0.17 (remove one row → perfect dependency)

Interpretation: the two metrics disagree in tone. Entropy looks weak at 0.50, because tiny samples magnify a single error. g₃ shows the dependency holds for 83% of rows, and the violation is one dirty record. In practice, a dependency with small g₃ suggests “use the hierarchy, and flag the data-quality issue.”

3.9Contextual inference: what the user didn’t say

Unstated constraints are latent variables z. We infer them the same way we inferred concepts:

z* = argmax_z P(z | Q, 𝒪 ) ∝ P(Q | z) · P(z | intent, ontology)

Example 1: a standard exclusion

The ontology records a curated rule that business metrics exclude test accounts:

P(exclude_test = true | metric = Revenue, curated rule) ≈ 0.95

Apply the rule by default and mention it.

Example 2: an unstated time window

“How has revenue been trending?” The intent is a trend (more in Module 4).

Candidate zP(z | trend intent)
All time0.20
Year to date0.30
Last 12 months0.50

The decision rule from Module 2 still applies:

P(z₁) = 0.50 < τ = 0.6 ⇒ not confident enough to apply silently

Action: use the last 12 months, and state the assumption explicitly so the user can correct it.

Decision theory view

Choose the constraint that minimizes expected loss:

z* = argmin_z Σ_{z'} P(z' | Q) · Loss(z, z')

With 0/1 loss, this reduces to “pick the most probable z”. With asymmetric loss, for example when silently including test data is far worse than excluding it, the choice can move away from the most probable option toward the safest one.

Explicit constraints always win

if the user states constraint κ explicitly: P(κ) = 1, override every prior

Priors only fill gaps. They never overwrite what the user actually said.

3.10Combining weak evidence

Relationships are often supported by several imperfect clues.

Chains (all links must hold): multiply

(A R₁ B) ∧ (B R₂ C) ⇒ A ~ C with conf = conf(R₁) · conf(R₂)

For example, 0.9 × 0.8 = 0.72. Confidence shrinks with every hop, which is why long inferred chains deserve scepticism.

Independent clues (any one suffices): noisy-OR

P(related) = 1 − Πᵢ (1 − pᵢ)

Example: a name match (0.6) and a value overlap (0.5) independently suggest the same link.

P = 1 − (1 − 0.6)(1 − 0.5) = 1 − 0.4 · 0.5 = 0.80

Independent clues reinforce each other, while chained clues dilute.

StructureCombinationEffect of adding evidence
Series (AND)ProductConfidence ↓
Parallel (OR)Noisy-ORConfidence ↑

A chain is a relay race: every handoff must succeed, so one weak handoff lowers the whole chance. Parallel clues are independent witnesses: any one can support the claim, so additional witnesses raise confidence.

3.11Putting it together: scoring a query plan

A complete plan π fixes the sources, joins, roll-ups and filters. Its overall score combines everything in this module:

log Score(π) = Σ_{e ∈ Steiner tree} log P(e) ← join validity (3.3–3.6) + λ₁ · sim( path concepts, C(Q) ) ← path meaning (3.5) − λ₂ · 1[fan-out on the measure] ← trap penalty (3.7) + Σ_{FDs used} log(1 − g₃) ← hierarchy soundness (3.8) + Σ_{latent z} log P(z* | Q, 𝒪 ) ← assumed constraints (3.9)
The best plan is π* = argmax log Score(π).

Every assumption made along the way is surfaced to the user.

Join validity, semantic fit, safe aggregation, hierarchy quality and contextual assumptions all contribute; a strong plan must survive each check.

Check your understanding

  1. Compute: a path has edges with P = 0.9 and P = 0.8. What are its total cost and its probability?Cost = −ln 0.9 − ln 0.8 ≈ 0.105 + 0.223 = 0.328. Probability = 0.9 × 0.8 = 0.72 (equivalently, e^(−0.328) ≈ 0.72).
  2. Compute: column A has 200 distinct values, B has 500, and they share 180. What are contain(A ⊆ B) and Jaccard? Which column is more likely the foreign key?contain = 180 / 200 = 0.90. Jaccard = 180 / (200 + 500 − 180) = 180 / 520 ≈ 0.346. A is likely the foreign key pointing to B: most of A’s values live in B, while B has many extra values.
  3. Compute: an order worth $50 joins to 4 line-item rows. What does a naive SUM report?$50 × 4 = $200, inflated by a fan-out factor of 4.
  4. Compute: two independent clues suggest a link with P = 0.7 and P = 0.4. What is the combined noisy-OR probability?1 − (0.3)(0.6) = 1 − 0.18 = 0.82.
  5. Reason: why must edge cost be −log P rather than 1 − P for shortest-path search to find the most probable path?Path probability is a product of edge probabilities. Only −log converts that product into a sum, so minimizing summed cost is the same as maximizing probability. Sums of (1 − P) have no such correspondence.
  6. Reason: a user asks “revenue last quarter, including test accounts”. What happens to the curated exclusion rule?The explicit constraint gets P = 1 and overrides the curated default. Priors fill gaps; they never contradict what the user stated.

Key takeaways

  • Data landscapes are graphs. Joins are edges with cost −log P(valid), so the shortest path is the most probable path.
  • Containment plus uniqueness beat column names as join evidence.
  • Steiner trees connect many entities at once, often through nodes the user never mentioned.
  • Valid joins can still give wrong numbers: watch for fan-out and chasm traps, and let measures travel only many-to-one.
  • Conditional entropy and g₃ reveal hidden hierarchies and their data-quality issues.
  • Unstated constraints are latent variables: fill gaps with priors, surface uncertain assumptions, and never override explicit instructions.
  • Evidence in series dilutes confidence, while evidence in parallel reinforces it.
