Module 2: Concept Mapping. How synonyms, abbreviations, typos and codes resolve to the same business concept.

2.1The problem: many words, one meaning

In Module 1, we assumed a function C(·) that turns a question into a set of concepts. This module shows how that function can work.

The same business idea appears in many forms:

FormExamples, all meaning Revenue
Synonymsales, turnover, income from sales
Abbreviationrev, REV, Rev.
Typorevnue, reveune
CodeR01, ACCT_4000
Domain jargontop line, bookings (sometimes)

The goal is a mapping from every surface form t to a concept c:

L : Surface forms → Concepts L("sales") = L("rev") = L("revnue") = L("R01") = Revenue

The difficulty is that the mapping is often ambiguous. “Sales” can mean revenue, units sold, or the sales team. So we need L to output a probability distribution over concepts, not a single answer:

L(t) → P(c | t, context)

given this word and the words around it, how likely is each business concept to be the one meant?

People say the same thing in many ways and different things in the same way. The system keeps a ranked list of “what you probably meant” instead of blindly picking the first guess.

It is a mail sorter reading messy handwriting. “Rev”, “revnue” and “R01” are different scrawls, but they all belong in the Revenue pigeonhole. When a scrawl could fit two pigeonholes, the sorter looks at the rest of the envelope for clues.

2.2Equivalence classes

Definition

Define a relation ~ on surface forms: t1 ~ t2 if both refer to the same concept. For ~ to be an equivalence relation, it must be:

PropertyFormalMeaning
Reflexivet ~ tEvery term means itself
Symmetrict1 ~ t2 ⇒ t2 ~ t1Synonymy goes both ways
Transitivet1 ~ t2 ∧ t2 ~ t3 ⇒ t1 ~ t3Synonyms of synonyms are synonyms

An equivalence relation partitions the vocabulary into disjoint classes:

[Revenue] = { revenue, sales, turnover, rev, top line } [Customer] = { customer, client, account holder, cust } [Region] = { region, territory, geo, area }

Every term belongs to exactly one class, and its concept is the class it lives in.

[Revenue]

revenuesalesturnoverrevtop line

[Customer]

customerclientaccount holdercust

[Region]

regionterritorygeoarea

An equivalence class is a “same-meaning bucket”. Every word goes in exactly one bucket, and words in the same bucket can be swapped for each other.

The transitivity trap

Real language is not perfectly transitive. Chaining loose synonyms causes semantic drift:

sales ~ revenue ~ income ~ earnings ~ salary ⇒ sales ~ salary ✗
strongsales
↔
strongrevenue
↔
mediumincome
↔
weakearnings
↔
driftedsalary

It is the game of telephone: each person repeats the message almost correctly, yet after five people it is a different sentence.

Fix 1: multiply confidences along a chain. Each link carries a confidence, and the confidence of a chain is the product of its links:

conf(t₁ ~ tₖ) = Πi=1k−1 conf(tᵢ ~ tᵢ₊₁)

For example, 0.9 × 0.8 × 0.6 × 0.5 = 0.216, which is too weak to trust.

Fix 2: only allow strict synonym edges to merge classes. Weaker relations such as related-to never merge classes. Instead they become distances (see 2.7).

2.3Surface similarity: edit distance

Typos and spelling variants are caught by measuring how many character edits separate two strings.

Levenshtein distance

The minimum number of insertions, deletions or substitutions needed to turn string a into string b. It’s computed with dynamic programming:

lev(i, j) = min { lev(i−1, j) + 1, (delete) lev(i, j−1) + 1, (insert) lev(i−1, j−1) + 1[aᵢ ≠ bⱼ] } (substitute)

fill a grid where each cell is the cheapest way to turn the first i letters of a into the first j letters of b: step down, step right, or step diagonally (free if the letters match).

Normalized similarity

sim_lex(a, b) = 1 − lev(a, b) / max(|a|, |b|)

Example: “revnue” vs. “revenue”

One insertion (the missing "e"), so lev = 1 max length = 7 sim_lex = 1 − 1/7 ≈ 0.857

Normalization first. Before comparing, apply cheap transforms such as lower-casing, trimming punctuation and reducing words to their stems (“revenues” → “revenue”). Many matches are exact after normalization.

Edit distance is the number of keystrokes (insert, delete, replace) a spell-checker needs to fix a word. Few keystrokes means probably the same word typed badly.

Edit distance knows nothing about meaning. “cost” and “coast” are 1 edit apart. “revenue” and “turnover” are 7 edits apart (almost every letter of “turnover” must be changed, and one extra letter added). This is why lexical similarity is only one input among several.

Used in the next section: s(t, c) is how closely t matches c’s known aliases, for example the maximum embedding cosine over the class [c]. ctx(c, Q) is how well c fits the other concepts in the question. λ is how much context matters. T is the temperature: a low T makes the distribution sharper and more decisive; a high T makes it flatter and more cautious.

2.4Resolving ambiguity: softmax over concepts

When a term could mean several concepts, we score each candidate and turn the scores into probabilities.

The model

P(c | t, Q) = exp( z(c) / T ) / Σc' exp( z(c') / T ) z(c) = s(t, c) + λ · ctx(c, Q)

score every candidate, exponentiate so that all scores are positive and bigger gaps count for more, then divide by the total so the answers add up to 1.

Context coherence

A concept fits better when it commonly appears with the other concepts already in the question:

ctx(c, Q) = Σcⱼ ∈ C(Q) \ {c} w(c, cⱼ)

Here w(c, cj) is how often c and cj appear together in practice. For example, “Revenue” with “Region” is common, while “Sales Team” with “Quarter total” is less common.

Worked example

Question: “Show sales by region last quarter.” The term is “sales”. Use λ = 1 and T = 1.

Candidate concepts(t, c)ctx(c, Q)z(c)
Revenue0.90.61.5
UnitsSold0.70.51.2
SalesDepartment0.80.10.9

Softmax:

e^1.5 = 4.482 e^1.2 = 3.320 e^0.9 = 2.460 Σ = 10.261 P(Revenue) = 4.482 / 10.261 ≈ 0.44 P(UnitsSold) = 3.320 / 10.261 ≈ 0.32 P(SalesDepartment) = 2.460 / 10.261 ≈ 0.24

Revenue wins, but not by much. How uncertain is this?

Measuring uncertainty: entropy

H(P) = − Σc P(c) · ln P(c) maximum = ln(number of candidates)
H = −[0.44·ln 0.44 + 0.32·ln 0.32 + 0.24·ln 0.24] ≈ 0.362 + 0.365 + 0.342 = 1.07 nats H_max = ln 3 ≈ 1.10 ⇒ normalized entropy ≈ 0.97 (very uncertain)

Entropy is a “confusion meter”. It is 0 when one answer has all the probability, and at its highest when every answer is equally likely. A normalized entropy of 0.97 means the system is almost guessing.

Temperature is how bold a judge is. At a low T the judge announces the top scorer loudly even if the lead is tiny; at a high T the judge shrugs and says “they all look about the same”.

What new context does

Suppose the user adds “…in dollars.” The unit “dollars” strongly fits Revenue, so ctx(Revenue) rises to 1.5 and z(Revenue) becomes 2.4.

e^2.4 = 11.023 Σ = 11.023 + 3.320 + 2.460 = 16.803 P(Revenue) ≈ 0.66 P(UnitsSold) ≈ 0.20 P(SalesDepartment) ≈ 0.15

A single word was ambiguous, but the surrounding words resolved it. Context is a form of evidence.

Decision rule

Accept the top concept only if it is both confident and clearly ahead of the runner-up:

accept c₁ if P(c₁) ≥ τ and P(c₁) − P(c₂) ≥ δ otherwise → ask a clarifying question, or state the assumption made

With τ = 0.6 and δ = 0.2, the first case (0.44, margin 0.12) leads to clarification. The second case (0.66, margin 0.46) is accepted.

2.5Abbreviations: the noisy-channel model

Think of an abbreviation as a corrupted message. Someone had a full form f in mind and sent a compressed version a. We want to recover f.

Bayes’ rule

P(f | a) ∝ P(a | f) · P(f) ───────── ──── "could f "how common shorten is f here?" to a?"

You get a text message that just says “NA”. You ask two questions: “could a sender abbreviate any of my candidate phrases this way?” (likelihood) and “which of those phrases is this person likely to be talking about right now?” (prior). The second question usually decides it.

Likelihood P(a | f): how plausible the shortening is

This is high when a matches f’s structure:

PatternExamplePlausibility
InitialsNA ← North AmericaHigh
PrefixRev ← RevenueHigh
Consonant skeletonMgmt ← ManagementMedium
SubsequenceQty ← QuantityMedium
No structural matchXYZ ← Revenue≈ 0

Prior P(f): how common the full form is

The prior should depend on context, not just global frequency. That is where most of the disambiguation happens.

Worked example: “NA”

Candidates: North America, Not Applicable, Net Amount.

Case A: no context. “What is NA?”

fP(a | f)P(f)ProductPosterior
North America0.90.30.270.27/0.81 ≈ 0.33
Not Applicable0.80.50.400.40/0.81 ≈ 0.49
Net Amount0.70.20.140.14/0.81 ≈ 0.17

The result is ambiguous: “Not Applicable” leads narrowly.

Case B: context is a region column. “Revenue for NA vs EMEA.” The neighbouring term “EMEA” is a region, so the prior shifts strongly.

fP(a | f)P(f | region context)ProductPosterior
North America0.90.850.7650.765/0.88 ≈ 0.87
Not Applicable0.80.100.0800.080/0.88 ≈ 0.09
Net Amount0.70.050.0350.035/0.88 ≈ 0.04

The result is now clear: North America.

The likelihood barely changed. The context-dependent prior did all the work. Never resolve an abbreviation in isolation.

“NA”, “N/A”, “Unknown” and empty strings often appear as placeholder values in data. A good mapping keeps them in a separate “missing or unknown” class rather than treating them as a real category.

2.6Codes in the data: pointwise mutual information

Internal codes such as “R01”, “ACCT_4000” or “ST-07” often have no linguistic structure at all. We can only learn what they mean from where they appear.

PMI

Measures whether a code v and a concept c appear together more than chance would predict:

PMI(v, c) = log₂ [ P(v, c) / ( P(v) · P(c) ) ]

compare how often the two really show up together with how often they would meet by pure coincidence. More than coincidence means a link.

PMI valueInterpretation
> 0Appear together more than expected: likely related
≈ 0Independent
< 0Appear together less than expected: likely unrelated

If two strangers are both tall and both like jazz, that tells you little. If two people show up at the same tiny jazz club far more often than chance allows, they probably know each other. PMI measures the “more than chance” part.

Worked example

Suppose we examine 1,000 documented field contexts, such as column descriptions, report labels and filters:

  • Code “R01” appears in 50 of them, so P(v) = 0.05.
  • Concept Region appears in 200, so P(Region) = 0.20.
  • They appear together in 40, so P(v, Region) = 0.04.
  • Concept Revenue appears in 300, so P(Revenue) = 0.30.
  • “R01” and Revenue appear together in 5, so P(v, Revenue) = 0.005.
PMI(R01, Region) = log₂( 0.04 / (0.05 × 0.20) ) = log₂( 0.04 / 0.010 ) = log₂ 4 = +2.0 bits PMI(R01, Revenue) = log₂( 0.005 / (0.05 × 0.30) ) = log₂( 0.005 / 0.015 ) = log₂ 0.333 ≈ −1.6 bits

Conclusion: “R01” is a region code, not a revenue code, even though both start with “R”.

Positive PMI (PPMI). In practice, negative values are noisy when counts are small, so they are often clipped: PPMI = max(0, PMI).

PMI exaggerates relationships for very rare codes. Common remedies are to require a minimum count, or to add a smoothing constant k to every count (P → (count + k) / (N + k·|V|)).

2.7Semantic distance in an ontology

Some concepts aren’t synonyms but are still close. “Gross revenue” and “net revenue” are siblings. “Revenue” and “cost” are both financial metrics, but they are opposites in practice. An ontology graph captures this structure.

The ontology as a graph

Edges are typed, and each type has a traversal cost:

Edge typeCost
synonym-of0 (same concept)
is-a / parent-of1
part-of1.5
related-to2

Method 1: Path-based similarity

dist(c₁, c₂) = weighted shortest-path length (e.g. Dijkstra's algorithm) sim_path(c₁, c₂) = exp( −μ · dist(c₁, c₂) )

With μ = 0.5:

PairPathdistsim_path
Gross Rev ↔ Net RevGross → Revenue → Net2e−1.0 ≈ 0.37
Gross Rev ↔ CostGross → Revenue → Financial → Cost3e−1.5 ≈ 0.22

Method 2: Information-content similarity (Lin)

The path method treats every edge equally. But two concepts that share a specific ancestor (such as Revenue) are more alike than two that share only a generic ancestor (such as Financial Metric).

Information content: IC(c) = −ln P(c), where P(c) is the probability that a random mention falls under c or any concept below it. Specific concepts are rare, so they have high IC.

sim_Lin(c₁, c₂) = 2 · IC( lcs(c₁, c₂) ) / ( IC(c₁) + IC(c₂) )

Here lcs is the lowest common subsumer: the most specific ancestor the two concepts share.

Assume the following probabilities:

ConceptP(c)IC = −ln P
Financial Metric0.500.693
Revenue0.201.609
Cost0.251.386
Gross Rev0.052.996
Net Rev0.082.526
sim_Lin(Gross, Net) = 2(1.609) / (2.996 + 2.526) = 3.219 / 5.521 ≈ 0.58 (lcs = Revenue) sim_Lin(Gross, Cost) = 2(0.693) / (2.996 + 1.386) = 1.386 / 4.382 ≈ 0.32 (lcs = Financial Metric)

Both methods agree on the order, but Lin separates the two pairs more sharply.

Path similarity counts steps on the map. Lin similarity asks how specific the shared ancestor is: sharing “Revenue” says a lot, while sharing only “Financial Metric” says little.

Why not just use embeddings?

Embedding models learn from which words appear in similar contexts. “Revenue” and “cost” appear in very similar sentences (“Q3 ___ rose 5%”), so their embeddings are often very close. An ontology encodes that they are distinct, even opposite concepts.

cos(φ("revenue"), φ("cost")) ≈ high ← embeddings: "these are alike" sim_Lin(Revenue, Cost) ≈ low ← ontology: "these differ"

Embeddings measure relatedness, while ontologies measure sameness. Concept mapping needs both.

Hot and cold are used in nearly the same sentences (“the water is ___”), so a reader of context alone thinks they are alike. A thermometer scale shows they sit at opposite ends. Embeddings are the reader; the ontology is the scale.

2.8Putting it together: a unified mapping score

Every signal from this module feeds a single score per (term, concept) pair:

z(t, c) = w₁ · cos( φ(t), φ(c) ) ← semantic relatedness (embeddings) + w₂ · maxt' ∈ [c] sim_lex(t, t') ← spelling / typo match (2.3) + w₃ · log P(t | c) ← abbreviation fit (2.5) + w₄ · PPMI_norm(t, c) ← co-occurrence for codes (2.6) + w₅ · Σcⱼ ∈ C(Q) sim_onto(c, cⱼ) ← ontology coherence with the question (2.7) + w₆ · log P(c) ← prior: how common or curated c is

Then:

P(c | t, Q) = softmax_c( z(t, c) / T ) (2.4) ĉ(t) = argmax_c P(c | t, Q) if P(ĉ) ≥ τ and P(ĉ) − P(c₂) ≥ δ else → clarify or state the assumption

Each signal is a witness. Embeddings say “sounds similar”, edit distance says “spelled similarly”, the abbreviation model says “could be a shortening”, PMI says “shows up with this concept”, the ontology says “fits the question”, and the prior says “common anyway”. The weights decide whom to trust for each kind of term.

Key takeaways

  • Synonyms form equivalence classes, but transitivity must be confidence-weighted to prevent drift.
  • Edit distance catches typos, noisy-channel Bayes expands abbreviations, and PMI decodes opaque codes.
  • Softmax plus entropy turns ambiguous terms into calibrated probabilities, and the τ / δ thresholds decide when to ask instead of guess.
  • Context-dependent priors do most of the disambiguation work.
  • Embeddings measure relatedness, while ontologies measure sameness. Robust mapping combines both.
